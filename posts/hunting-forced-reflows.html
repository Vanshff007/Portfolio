Hunting forced reflows on a no-framework site

My portfolio is plain HTML, CSS and JavaScript. No framework, no build step. That does not make it fast by default. Lighthouse found the main thread stuck on layout work I had written myself.

What a forced reflow is

The browser batches layout: you change styles, and it works out positions later, once per frame. But if you read a layout value (scrollHeight, getBoundingClientRect(), offsetTop) right after a change, the browser has to do the layout now, synchronously, to give you a correct number. Do that in a loop or on every scroll event and it adds up fast.

Fix 1: the scroll progress bar (about 60 ms)

The bar at the top of the page read document.documentElement.scrollHeight on load and on every scroll. Lighthouse measured about 60 ms of forced layout on load from that one line.

The page height only changes when the layout changes, so now it is cached and refreshed by a ResizeObserver and on window resize. The scroll handler only reads scrollY, which is cheap.

let maxScroll = 0;
function measure() {
  maxScroll = document.documentElement.scrollHeight - innerHeight;
  onScroll();
}
new ResizeObserver(measure).observe(document.body);

That one change took the Lighthouse performance score from 88 to 98.

Fix 2: the journey timeline (about 113 ms)

The timeline line draws itself as you scroll, and each item lights up when the line reaches it. The old handler toggled a class on one item and then read the next item's rect. Read, write, read, write: one forced layout per item, about 113 ms on load.

The fix follows one rule: all reads first, then all writes.

  • Item offsets come from offsetTop once, in a ResizeObserver, not on every scroll.
  • Each frame reads one rect (the list's), then writes the line's transform and the classes.
  • Scroll work is throttled to requestAnimationFrame, and it runs only while an IntersectionObserver says the timeline is on screen.

Fix 3: work that ran on every frame

Even with the mouse still, the page did style and layout work on every frame, and the pointer felt laggy. The causes were small:

  • The scroll hint animated left, which is a layout property. Now it animates transform.
  • The "live" dots pulsed with an animated box-shadow, which repaints. Now a second dot scales and fades.
  • The hero's particles and CSS animations now pause while the hero is off screen.

Fix 4: a cursor that repainted the screen

The custom cursor is a dot and a ring that follow the pointer. They moved with translate, so no layout, but every move still repainted the area under them, and that includes a full-screen noise texture. On integrated graphics at 144 Hz, frames dropped and the cursor fell behind.

.cursor, .cursor-ring { will-change: translate; }

One line gives both their own compositor layer, so moving them repaints nothing. The cursor also stops its animation loop once the ring catches up, so an idle mouse costs nothing.

What I took away

  • Read Lighthouse's "Avoid forced reflow" list. It names the function and the time.
  • Cache layout values and refresh them from observers, not from scroll events.
  • Animate transform and opacity. Anything else, check the Performance panel first.
  • Pause what is off screen.

The site now scores 91 for performance and 100 for accessibility, best practices and SEO (live site, median of 3 runs).
